# S4 reviewed publication workflow — 17 November 2026

This records infrastructure delivery before the first owner approval. The subsequent 20 approved additions and current counts are documented in [batch 01 delivery](status-s4-batch-01.md).

The converter can now expand the reading edition through explicit publication selections. Previously it selected only the fixed S2 validation/trial items, independently of decisions saved in `/review/`. This increment connects owner-reviewed proposals to repeatable conversion and provides full source text for local review.

## Workflow

1. Run `pnpm publication next` to generate the next read-only batch of up to 20 pending work proposals in `reports/publication-next.md` and `.json`. `--action split` or `--action merge` selects the corresponding structural proposals. Already published targets and source selections that conflict with the existing edition are excluded; rejected candidates and reasons are recorded in the JSON packet. These packets are not publication approvals.
2. Run `pnpm dev` and follow the packet's local `/review/` links. Each proposal opens the right queue page and scrolls to its card. **Read the full source** opens the complete recovered text and its SHA-256 in a separate tab, retaining the review form. Reference destinations are shown as inert text so that a wrapper page linking to an attachment can be distinguished from the work itself. This view reproduces source text, not the original visual layout or illustrations. IT/EN interfaces are available.
3. The owner explicitly approves or defers each structural proposal with a reason. No classifications are approved by this decision. `pnpm publication status` lists current approvals that are eligible for selection and the existing edition selections.
4. Run `pnpm publication select <proposal-id> --dry-run` to validate a candidate without writing. Run the same command without `--dry-run` to record the whole reviewed proposal in `data/publication.json`. A split selects all its targets together. Decisions remain in `data/review-decisions.json`; selecting a proposal never edits them. `pnpm publication remove <proposal-id> [--dry-run]` removes an explicit selection while preserving the original S2 baseline.
5. Run `pnpm build`. Conversion includes the baseline plus selected additions; all reading texts receive the existing source-fidelity, image/anchor/table, link/privacy, source-page, search and historical-index checks. Successful build is required before deployment. Commit the publication manifest with the resulting verification evidence using the existing private deployment workflow.

## Invariants and limits

- The baseline is pinned in `data/publication-baseline.json`, independently of regenerated selection reports, and binds the fixed validation sample by fingerprint. The 43 canonical baseline items and three legacy previews are retained. The recorded 30-item random validation sample is unchanged. The live publication manifest is initially empty; this increment publishes no additional text and records no owner decisions.
- A proposal needs a current explicit **approved** decision in the owner ledger. An `approved` label in proposed item metadata is insufficient; a deferral invalidates selection. Fingerprints bind approvals to source hashes and structure, and publication selections additionally pin reading routes, language and contribution metadata. Changed selections fail conversion rather than silently changing the edition. Reconcile stale decisions through an explicit new review; never replace a fingerprint just to retain an approval.
- Publication accepts supported HTML/PDF reading items from work/split/merge proposals. Their sources must belong to the reviewed proposal. World publication, technical indexes, standalone attachment records and other formats are not enabled by this increment.
- New items cannot overlap existing whole-document or fragment selections. Adjacent disjoint fragments are allowed. Replacing an existing edition with a conflicting editorial structure remains a separate reviewed operation; the tool never removes old editions to resolve a conflict automatically.
- Manifest updates use an exclusive lock and atomic replacement. Concurrent writers fail without replacing another selection. The live ledger, source files and publication manifest are untouched by status, next and dry-run commands. Tests use temporary fixture directories only.
- Full review source routes remain local and development-only, inherit the existing host/loopback restriction, accept GET only and verify original hashes. Archived HTML is rendered as escaped plain text; scripts, emails, active links and executable attachments are not served. Publication selections and next-batch reports are absent from the production output.
